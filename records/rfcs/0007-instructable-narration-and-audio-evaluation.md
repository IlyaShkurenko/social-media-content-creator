# RFC-0007: Instructable hook narration and Gemini audio evaluation

- Status: Accepted
- Date: 2026-08-18
- Decision owners: Project maintainers and product owner
- Decision type: TTS provider, LLM-generated delivery direction, paid audio evaluator

## Summary

Add a second, instructable narration provider (OpenAI `gpt-4o-mini-tts`) alongside
the existing free Azure/edge-tts default, let the campaign concept planner emit a
per-hook delivery direction that steers it, and add a Gemini-based audio judge
that scores the rendered narration for naturalness and emotional match. All three
pieces are additive: the existing Azure narration path is unchanged when no
delivery direction or OpenAI voice is requested.

## Context

`en-US-JennyNeural` (Azure/edge-tts) is the only narration voice the campaign
pipeline has used. It has fixed per-voice prosody: no per-line control over
pacing, emphasis, or emotional colour, which reads as flat/"AI narrator" for
short, emotional ad hooks. Manual comparison against OpenAI's `gpt-4o-mini-tts`
confirmed a real, audible improvement is possible, but only within a narrow
band: an `instructions` string that describes character state ("a genuinely
confused, quietly anxious person thinking out loud") worked; a string that
issued literal audio-engineering directions ("do not soften the final
syllable") produced an over-acted, more robotic result than the plain Azure
baseline. Naturalness is a perceptual judgment neither an LLM instruction
author nor this agent can verify from text alone — it requires either a human
listener or an audio-capable judge.

## Decision

### 1. Hook delivery direction is planner output, not hand-authored

`AdvertisingConcept` gains `hook_voice_delivery: str`, generated by the same
Gemini call that already produces `hook_voiceover` and `target_emotion`. It
must describe the character's emotional state and situation, not literal
prosody mechanics (volume, syllable stress, fade behaviour) — the distinction
that separated the working manual instruction from the over-acted one.
`compile_concept_storyboards` copies it onto the compiled hook scene as
`StoryboardScene.voice_instructions`; product-demo and CTA scenes keep it
`None` and fall back to provider-default delivery. A superseded raw beat
carries no delivery direction into the compiled contract, matching the
existing rule that only compiled content is model- or synthesizer-visible.

### 2. OpenAI narration is one more provider behind the existing dispatch

`app/services/voice.py` gains `is_openai_voice()` / `openai_tts()`, matching
the shape of `chatterbox_tts()` (both speak the OpenAI-compatible
`/audio/speech` contract) but pointed at `api.openai.com` with a real bearer
key from `config.app.openai_api_key`, model `gpt-4o-mini-tts`, and a new
`instructions` argument threaded through `tts()`'s existing keyword-argument
pattern. Voice selection follows the established `provider:voice` convention
(`openai:cedar`). `resolve_narration_voice`'s content-language-prefix check is
relaxed to also accept the other providers' existing non-prefixed formats,
which it never actually enforced correctly for them.

### 3. Campaign narration cost is ledger-tracked; every other caller is unaffected

Per `goal.md`'s existing rule ("Any paid planner, TTS, vision judge, or
generated-media call introduced later must use this same scope"),
`generate_scene_narration` accepts an optional `budget_ledger` /
`operation_prefix`. When the resolved voice is an OpenAI voice, each scene
reserves and charges a fixed conservative per-scene estimate
(`OPENAI_TTS_SCENE_WORST_CASE_MICROUSD`) against `mixed-media-iteration-001`
before synthesis, exactly as Gemini judge calls do; when it is absent, no
ledger call happens, so free-tier Azure narration is byte-for-byte unaffected.
The estimate is a fixed ceiling rather than a metered actual, because the
streaming-to-file response path does not expose OpenAI's per-call token usage;
a future refinement may switch to the non-streaming response form to record an
exact charge the same way Gemini calls do.

### 4. A Gemini audio judge is pairwise, diagnostic, not a gate

Evaluator `1.0.0` scored one clip in isolation against absolute criteria
(met/partially_met/not_met). A live sanity check against five real narration
clips — one where a human had explicitly identified an "absurd, tender"
ending and one called "the most robotic of all" — falsified it: every clip
scored a perfect `1.0` on every dimension, including the two known-bad ones.
This mirrors exactly why `gemini_judge.py`/`invariant_judge.py` never score
video absolutely: an LLM judge without a comparison anchor is not
discriminating. Evaluator `2.0.0` replaces absolute scoring with the same
pairwise pattern those video judges already use: `GeminiAudioJudge.compare()`
sends two clips as separate inline audio parts in one request (audio clips
here are single-digit KB to low hundreds of KB, well under the 20 MB inline
limit) and asks Gemini which clip wins on naturalness, target-emotion match,
and — specifically, because this is the defect that exposed `1.0.0` — which
holds delivery consistent through the end of the line rather than trailing
off or turning tonally mismatched. Two passes reverse which physical clip is
labelled A/B; a clip preferred in both is real signal, a clip that wins only
by position cancels to a diagnostic tie, identically to
`build_winner_diagnostic`.

A pairwise call only ever compares two clips. `round_robin_compare()`
extends this to `N` candidate voice variants by running every unique pair
(`N·(N-1)/2` pairs, each two passes) rather than anchoring every variant
against one fixed reference: a full round robin was the deliberate choice
here (see the accompanying discussion) over the cheaper, linear
anchor-against-one-baseline pattern the video judges use, because the
motivating question was "rank these voice options against each other," not
"is this one candidate acceptable against the accepted production baseline."
It produces a leaderboard of average pairwise preference credit per label —
diagnostic ranking evidence, not an acceptance decision.

Both the single-pair and round-robin paths follow the same fail-closed
ledger pattern as the video judges: ambiguous provider outcomes (5xx,
timeouts, the same non-4xx set already classified in `gemini_judge.py`)
retain a worst-case charge per pass and a pass already holding a ledger
operation is never resubmitted. No automatic accept/reject decision is wired
to this evidence. Establishing it as a calibrated acceptance signal requires
the same labelled-baseline discipline as RFC-0006's video evaluators, and is
out of scope here.

## Consequences

The campaign pipeline can generate a second, more expressive narration option
per hook without touching the default free path, and the delivery direction
that steers it comes from the same structured concept data the storyboard
compiler already trusts, not from ad hoc prompt text. The audio judge gives a
cheap, repeatable first pass before spending human listening time, but does
not yet decide anything on its own.
